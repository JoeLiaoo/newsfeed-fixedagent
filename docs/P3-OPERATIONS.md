## 安全启动

运行 npm run member:seed-gp（在数据库迁移后）导入候选。初始 9 个候选主体来自 `reference/母基金已投子基金管理人.md`，均为 `candidate`，不自动认定基金管理人等于直接投资 GP。在 `/settings/admin-gps` 确认主体名称、唯一实体 ID、GP/管理人/基金角色及公开证据后，才允许启用监测。首次完整快照作为历史基线；以后新增的投资关系标为 `observed`，不能凭新华财经入库日期或更新时间判定为“当日投资”。管理员提供**独立事实证据 URL + 真实事件日期 + 赛道**后，才可标记为 `verified`，进入每日 GP 汇总。

这三个开关在新环境默认关闭：`P3_GP_SYNC_ENABLED`、`P3_NOTIFICATIONS_ENABLED`、`P3_DELIVERY_ENABLED`；当前生产实例按用户指示开启。开启状态不代表 GP 内容已核验或定向送达已验收。模型 `MODEL_CALLS_ENABLED=true` 时可建议四大产业细分赛道，结果仅供管理员复核；不允许战略配售标签参与 GP 匹配。

员工清单 `GET /api/v1/membership/gp-projects` 和单项详情 `GET /api/v1/membership/gp-projects/:id` 使用同一会话鉴权与可见范围：仅有效 GP 的 `verified` 投资；无会话返回 401，未知、未核实或 GP 已暂停的项目详情返回 404。详情仅返回项目名称、GP 名称、审核赛道、日期、状态与可展示来源；内部原始证据和审核人字段不下发。演示域名来源仍标作占位。发布后可用已审核项目及隐藏状态项目各核对一次，不能凭列表存在推断真实投资事实已验收。

GP 通知生成和发送前重验复用员工清单的来源地址检查：`example.org`／`example.com`／`example.net` 及子域名只显示“演示/导入占位 · 无可核对来源”，不会把占位 URL 送到微信；有效 HTTPS 来源仍显示原链接。通知匹配只纳入有效 GP，且“战略配售”不参与兴趣匹配。此代码行为仍须在真实 GP 事实和手机端通知中验收。

## 员工扫码绑定与聊天

**2026-10-22 方案决策：** 不使用企业微信或公司审批流程，允许员工在 iLink 会话窗口失效后主动向自己的 bot 发消息恢复推送。选择 [每用户独立 iLink 扫码登录设计](P3-ILINK-QR-DESIGN.md) 为 PR #15 的后续目标：登录网站 → 短期二维码 → 微信扫码确认 → 网站自动绑定。员工不需要网页绑定码或点击二次确认。每个人是否使用独立 bot 是实现细节，当前 PoC 先验证每人一组可用的 iLink bot 身份。

**历史状态（2026-10-22）：** [PR #15](https://github.com/JoeLiaoo/newsfeed-fixedagent/pull/15)（merge `acef3866367d`）实现个人短时 iLink 扫码授权、可信身份自动绑定、每用户独立加密凭据与长轮询上下文、按人定向推送及互动后恢复。该代码已随 `main` 提交 `5031e2c04dec382263d05b38484b0cfaabeaa15b` 发布，迁移 `0152`–`0155` 已应用。2026-10-22 按用户指示启用扫码、GP 同步、通知生成与投递四项开关；当日有 3 个 active 平台账号、0 个微信绑定与 0 个 iLink 账号。**最新状态（2026-10-23）：** PR #22 已发布；两个绑定账号各一条测试通知由 iLink 接受，用户确认两台手机均收到。跨日投递、互动窗口失效与恢复仍待确认。普通 Hermes Agent 多 Bot 对话尚未接入新推送通道（旧 Hermes 网关保留），与推送授权分离。部署细节见[PR #22 发布记录](logs/2026-10-23-P4-pr22-deployment.md)、[双用户抽测记录](logs/2026-10-23-P3-04-live-push-smoke.md)、[收件确认记录](logs/2026-10-23-P3-04-handset-receipt.md)及[开关启用记录](logs/2026-10-22-P3-flags-enabled.md)。

上游现有能力及尚需实测的关键差异：
- [腾讯 openclaw-weixin 协议](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol_zh_CN.md)定义二维码生成与状态轮询，确认后可包含 `ilink_user_id`、`ilink_bot_id`、`bot_token`；还可能有微信端验证码、重复绑定、超时与区域重定向。
- 当前 [Hermes iLink 文档](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/weixin.md)仅说明单账号网关配置；多 profile、多 bot token 同时轮询、逐用户主动发送，需原型验证。腾讯 OpenClaw 插件的多账号特性不等于 Hermes 已实现。
- 用户接受主动消息窗口失效后在微信向 bot 发一条消息恢复，但对 24 小时/10 条的流行说法只能视作第三方经验，不能当作官方承诺。需根据真实渠道响应，区分「需要互动」与「需要重新扫码」。

绑定资格仅赋予网站 `active` 用户；每个扫码会话短时、一次性并与有效网页登录会话关联。iLink 确认结果由服务器直接读取，`bot_token` 加密存放，不得返回浏览器或写入日志。普通聊天权限由 Hermes pairing/allowlist 独立控制；扫码和推送订阅不提升其权限。解绑、退订须立即撤销后续投递授权；新账号资讯与 GP 开关默认开启，不覆盖用户已有选择。

出站已有平台 outbox 的版本、权限重验、幂等与 `accepted` 语义，原则上继续复用；但当前插件仅有全局 `_adapter`，**不支持路由不同 Bot**；新账号已改由按 Bot Token 隔离的 iLink worker 发送，并有双用户模拟测试，尚需真实微信验收。原有 `/api/v1/membership/bridge/claim`、`/weixin/confirm` 手动验证码协议已弃用；`/weixin/start` 现在创建仅属于当前已批准网站会话的**iLink 专属二维码**，`/weixin/status` 经腾讯状态回执自动绑定。新用户独立 iLink 出站由 worker 处理，不复用旧 Hermes 单例 `_adapter`；旧 `/deliver` 仅供兼容历史帐号的受控测试。

**扫码确认由服务端完成（2026-10-22 生产实测后的修复）。** 员工在手机上确认二维码时网页往往已经切到微信或另一个标签页，旧实现只在网页请求状态时才去问腾讯，因此服务器一直没有写入绑定。现在 worker 注册 `membership.ilink-scan`（受 `P3_ILINK_BINDING_ENABLED` 控制，每分钟一次），对未过期的扫码会话自行查询渠道状态，确认后写入绑定；过期会话标记 `expired`，用户可以重新生成。网页在标签页重新可见时立即查询一次，隐藏时降频继续查询，绑定成功后显示已有的「已绑定」状态。

渠道查询失败时 `/weixin/status` 返回 HTTP 502 与 `status=error`，不再返回 `wait` 掩盖错误；网页显示一行失败状态并提供「重新生成二维码」，被标记为 `error` 的扫码会话可以被新二维码替换（未过期的正常扫码会话仍然拒绝重复生成）。旧二维码的查询若在替换后才返回，页面与 worker 都按原二维码的加密值核对当前扫码，忽略旧结果；旧身份不得绑定到新会话。收到某账号第一条入站消息时机器人回一句「已连接，之后会在这里推送。」，每个账号只回一次（`member_ilink_accounts.greeted_at`）；这条确认与其它渠道发送一样受 `P3_DELIVERY_ENABLED` 控制，不做其它自由聊天回复。记录见[服务端确认绑定日志](logs/2026-10-22-P3-04-server-side-binding.md)及[PR #18 评审修复日志](logs/2026-10-23-P3-04-pr18-review.md)。

绑定页点击扫码后应在新标签页显示官方二维码，原标签页保留并显示扫码结果；成功或失败后可关闭二维码标签页。若浏览器拦截弹出页，可点击页内「打开微信官方二维码」手动打开。绑定成功后先向 Bot 发送一条消息，等待「已向机器人发送消息」自动勾选；若后续投递被渠道明确判为需重新互动，该框取消勾选，再发消息可恢复。该勾选只表示服务端收到过消息且当前已知通道状态可用，不代表下一条消息已送达。见[本次交互记录](logs/2026-10-23-P3-04-binding-feedback.md)。

原始部署与回退记录仍见[历史部署日志](logs/2026-10-22-P3-wechat-flow.md)，其流程描述是历史状态，不作为现行产品方案。部署／迁移验证、PoC 和真实双员工验收均按新设计文档执行。

## 日历与调度

平台 worker 北京时间每小时轮询经核准的 GP（仅开启后），每天按工作日资讯 09:00 / GP 10:00、休息日资讯 11:00 / GP 12:00 分别生成两类消息，按用户兴趣过滤并去重，超长正文按 1600 字符上限分片发送，空内容仍发“今日无更新”。outbox 为每个来源片段保存原文偏移；重验只更新并恢复该片段，不会将整条长资讯重复写入每个分片。每 5 分钟领取 outbox 发送。首次推送从绑定时刻起算；不补发历史基线。

必须由运维根据官方节假日、补班表设置 `P3_CN_HOLIDAYS` 和 `P3_CN_MAKEUP_WORKDAYS`（均为半角逗号分隔 YYYY-MM-DD）。若未配置，系统只能识别通常周末，不能准确覆盖国家法定假期。

## 验收清单

1. 真实新华财经：主体唯一 ID 核实、完整分页/上限及数据授权；至少一组已知 GP 关系快照复查。
2. 真实 DeepSeek：四类细分赛道准确率、低证据时空分类、费用、限流及人工修订。
3. 两个经管理员批准注册的平台账号：分别扫描网页专属二维码，无网页验证码或确认操作，由 iLink 登录回执自动绑定到正确的收件人；若微信端要求额外验证应如实展示。扫码绑定不得绕过 Hermes pairing；收信身份、各自默认订阅、跨日窗口与互动恢复须实测。选择不同兴趣后只收到各自匹配内容；退订/解绑即时生效。至少连续 3 天跨日主动投递，包含普通日和可核验的休息日。
4. 渠道故障：401/410、429、超时、accepted 与未知回执；检查是否会重复投递或越权读取。
5. P3 联调前确认不触碰旧版归档及服务器其他服务；旧版本无备份恢复前置要求。新平台正式运行仍按 P4 完成自身备份恢复方案。

## 合并后的上线限制与恢复原则

P3 的数据表、服务端接口和后台管线可以与主分支共同发布，但 **PG 同步、通知生成、渠道发送全部保持默认关闭**。
代码合并不代表已接入实际新华财经/DeepSeek/Hermes，不得启用三个 P3 feature flags，直到渠道授权、真实环境联调与双用户跨日验收完成。

- GP 实体一旦产生任意抓取快照，`entity_id` 和 `entity_role` 即被冻结；核验纠错须新建候选并重新建基线，不得将另一实体历史关系误判为新投资。
- `baseline` 与撤回记录不得直接核准为新增；已核准记录的分类/来源修改不会刷新首次核准时间。
- `member_gp_snapshot_evidence` 保留不可变的每期原始响应（包括不完整快照），`member_gp_review_audit.before_state/after_state` 保留人工核准历史。上线前核实数据保留期限、访问权限与敏感字段。
- 专家任务、产物和模型回执按业务用户及任务关联；七天任务到期清理会删除产物与模型回答正文，并保留用量、费用和哈希审计字段。
- 网页和新闻通知共用同一用户/日期日报版次、截止时间、偏好版本及来源集合。每期 outbox 持久化截止点和来源片段关系；发送前按当前新闻可见状态、GP 核验状态和用户兴趣重新核查，并在 1600 字符上限内更新文本。来源撤回时取消对应消息并释放未发送的去重预占。
- 通知设置原样保存不改变版次或待发消息；新闻与 GP 使用各自订阅版次，暂停、退订和绑定变更会取消相应的 `pending`、`failed`、`sending` 记录并释放来源预占。发送器在重验后再次检查用户、绑定和订阅版本，并通过与退订／解绑共用的用户事务锁串行化最终检查和桥接请求；请求已开始后，设置变更会等待该请求结束。用户+类型+来源键及 outbox 关联在同一事务写入；额外回扫最多 48 小时的变更来覆盖晚提交事务，旧版发布日期不直接用作增量游标。
- GP 分类每 5 分钟从持久待办选择最多 20 条；失败最多重试 3 次。通知生成按北京时间 09–23 点每小时恢复，若错过正常时点，同一天晚些时候仍可生成当期消息。
- 专家任务崩溃恢复在同一数据库事务内更新任务并写入 pg-boss 队列；最多执行三次，超过上限进入失败终态。
- 目前仅识别第一次新增的 **GP－被投企业关系**，不声称监控同一企业的所有后续融资轮次。

## 运维检查与失败处置（未来启用时）

1. **准备环境：** 先取得服务器所有人的备份与恢复确认，执行只读盘点；核对数据库迁移 `0116`–`0151`、用户权限、加密传输、后台登录、日志脱敏，以及 `.env` 中三个开关仍是 `false`。不要将任何密钥、绑定码、真实用户的原始响应贴入 PR 或公开日志。
2. **核准 GP：** 执行 `npm run member:seed-gp`（在迁移之后）；管理员进入 `/settings/admin-gps`，逐一核对 9 个候选角色、唯一 ID 和证据，并仅对真实 GP 设为 `active`。身份产生快照后即冻结，纠错需创建新主体并重新建立基线。检查完整/不完整快照及不可变证据，确认首次完整快照均为 `baseline`。
3. **核准事件：** 校验投资关系真实发生日期、独立 HTTPS 来源与赛道；`observed → verified` 必须由管理员完成。重复调整不会生成新的首次核准事件；`baseline`、`retracted` 不能升级为新增。AI 分类是建议，不是事实证明。本系统当前仅跟踪首次发现的 GP→企业关系，不跟踪同一家企业每一轮追加融资。
4. **联调微信：** 在取得个人同意及渠道使用条件核对后，先依照 [独立 iLink 扫码设计](P3-ILINK-QR-DESIGN.md)完成双用户 PoC，核对可信扫码身份、不同 bot 收发、互动恢复、退订与解绑。旧 HMAC 绑定码流程不得重新启用。**`accepted` 只表示桥接侧已受理，不能作为微信实际送达证据。** 扫码确认由 worker 完成，PoC 时网页可以切到微信后台；回到网页应显示「已绑定」，若显示失败状态则重新生成二维码后重试。
5. **分阶段激活：** 服务商主体及快照验收后，才考虑打开 `P3_GP_SYNC_ENABLED`；人工核准与内容核验后再试运行 `P3_NOTIFICATIONS_ENABLED` 生成 outbox；只有真实 sidecar 的幂等协议和两个用户收件人验证完成，才考虑打开 `P3_DELIVERY_ENABLED`。每阶段先检查数据库记录和健康状态，再进入下一阶段。
6. **故障与回退：** 任一环节出现错收件人、重复发送、未授权数据、异常大量新增或不明送达结果，应立刻关停 `P3_DELIVERY_ENABLED`，必要时同步关闭另外两个开关；保留审计、outbox 与快照供复核，不盲目重发 `unknown`，也不删除数据库表。收件会话失效（410 / `requires_rebind`）走重新绑定；限流（429）按受控重试检查。

通知采用固定读取截止时间、48 小时回扫与用户级去重；这 **不保证** 任意长期延迟的历史数据都能自动补送。生成任务只在同一北京时间自然日内迟到恢复，跨日断服务需人工核对并决定是否补发。中国法定节假日和调休表必须按官方日历维护，未配置不能声称节假日时刻准确。生产验证前，保留 P3 四项未完成状态。
