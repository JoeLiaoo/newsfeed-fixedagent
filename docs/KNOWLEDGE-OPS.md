# 知识库运行手册

全公司共享投研知识库的存储、权限、保留、备份、费用与排障说明。需求基线见 [PLAN.md §12](PLAN.md#12-全公司共享投研知识库)，任务状态见 [IMPLEMENTATION.md](IMPLEMENTATION.md)。

## 1. 范围与使用者

- 知识库是**全公司共享**的数据域：已批准（`status='active'`）的平台员工都能浏览、检索、问答和下载原件。
- 库按**库**组织（[Issue #36](https://github.com/JoeLiaoo/newsfeed-fixedagent/issues/36)）：平台默认带一个「知识库示例」（`id='shared'`），它承载本功能上线以来入库的全部材料；员工可在页头「+ 新增知识库」再建一个库。每个库有自己的材料、知识页、构建任务与问答，互不混用。
- 未登录或未通过审核的账号在访问边界就被拒绝（`registerMembershipAccessBoundary`），拿不到任何页面、接口或文件。
- 员工上传后**自动进入所在库**，没有逐条管理员发布环节；管理员也不逐条审稿，只在必要时撤回。
- 上传者、来源（机构／作者／日期）和每一步处理都写入审计事件（`member_wiki_audit_events`）。

## 2. 数据模型

| 表 | 内容 |
|---|---|
| `member_wiki_bases` | 一个知识库：名称、说明、状态（`active`／`archived`）、创建人 |
| `member_wiki_documents` | 一份材料（逻辑文档）：标题、上传者、所属库、状态（`active`／`withdrawn`）、撤回人与时间 |
| `member_wiki_document_versions` | 材料的每个版本：文件字节、校验和、格式、上传者填写的原始来源（标题／作者／机构／日期／类型）、提取文本与提取状态 |
| `member_wiki_tasks` | 一次构建：阶段、状态、尝试次数、错误码、编译草稿与复核结果（检查点）、租约 |
| `member_wiki_pages` | 一个知识页：标识、页面类型、标的、赛道、状态、标的稳定标识（`target_key`）、所属库 |
| `member_wiki_contributions` | 每份材料版本对某个标的的结构化贡献：贡献内容（页面草稿与来源）、状态（`active`／`superseded`／`withdrawn`）、所属材料与版本 |
| `member_wiki_page_revisions` | 页面的每个修订：正文、覆盖度统计、来源构建任务与材料版本 |
| `member_wiki_citations` | 页面的引用锚点：来源标签、定位、分析师、机构、日期、所指材料版本 |
| `member_wiki_quality_issues` | 质量问题：等级（`P0`／`P1`／`advisory`）、类别、目标、说明、证据 |
| `member_wiki_audit_events` | 处理审计：上传、构建成功／失败、重试、撤回、问答 |
| `member_wiki_answers` | 问答记录：问题、回答正文、引用、覆盖范围、时效分档、所用页面 |

迁移文件在 `modules/membership/migrations/0157_…` 至 `0175_…`，每个文件一条语句（在线迁移约定）。多知识库的迁移为 `0176_…` 至 `0180_…`：新建 `member_wiki_bases`，给材料与知识页各加一列 `base_id`（常量默认值 `'shared'`，上线前的材料与页面因此自动归入共享库），并为两列各建一个索引。

### 2.1 多个知识库怎么分开

- **材料与页面各有一个 `base_id`**；构建任务、贡献、修订、引用与质量问题都从材料或页面派生，因此不再单列。
- **页面的 `target_key` 与 `slug` 按库分开**：共享库沿用上线前已有的 `target_key` 与 `slug`（如 `view-company-example`），因此已发布的页面仍是共享库的页面；其他库在前面加自己的库号（如 `kb-1a2b3c4d5e6f|view|公司|某公司`、`kb-1a2b3c4d5e6f-view-company-example`）。同一标的因此可以在两个库中各有一页，互不合并、互不引用。
- Builder 原始 slug 上限为 80 字符；问答使用发布后的完整标识（含库前缀与消歧后缀），上限为 128 字符，不截断已有页面地址。
- **问答只在本库内路由**：提问时带上库号，候选页面只取该库已发布的页面；库里没有覆盖时返回 `knowledge_no_coverage`。
- **问答记录按库派生**：`member_wiki_answers` 没有 `base_id` 列，回答与库的对应关系由它记录的 `pages`（回答用过的知识页 slug）推导——用过的页面里有一个属于该库，这条回答就算该库的回答。`GET /answers` 只返回 `asked_by` 为当前员工的回答：问答记录是员工自己的记录，文档未定为库内共享。
- 规则与换算写在 `modules/membership/knowledge/bases.ts`（`scopedTargetKey`／`scopedSlug`／`baseSlugOf`），改库的空间规则只改这一处。

## 3. 接口

全部在 `/api/v1/membership/knowledge/` 下，均需员工会话：

| 方法与路径 | 用途 |
|---|---|
| `GET /bases`、`GET /bases/:id` | 知识库列表（名称、说明、材料数、知识页数、构建中／失败数）与单个库 |
| `POST /bases` | 新增知识库：名称（2–80 字）与说明（≤200 字）；已批准员工均可创建 |
| `GET /overview` | 库内材料数、知识页数、构建中／失败数、未决质量问题、时效分布（`?baseId=` 指定库，缺省为共享库） |
| `GET /documents`、`GET /documents/:id` | 材料列表（可检索，`?baseId=`、`?query=`）与单份材料的版本、构建状态（已撤回的材料只对上传者与管理员可见） |
| `POST /documents` | 上传：文件名、base64 正文、标题、作者、机构、日期、类型、所属库 `baseId`、可选的 `documentId`（作为新版本）；日期须为真实有效的 `YYYY-MM-DD`，无效值返回 `knowledge_date_invalid` |
| `POST /documents/:id/withdraw` | 撤回材料：它的贡献退出所在库，由它生成的知识页重新聚合或下架 |
| `GET /tasks`、`POST /tasks/:id/retry` | 库内构建状态列表（分页：`?limit=`（1–100，默认 50）、`?offset=`，返回 `hasMore` 与 `nextOffset`）；重跑失败的任务（从上次成功的检查点继续） |
| `GET /pages`、`GET /pages/:slug` | 已发布知识页列表（可检索，`?baseId=`、`?query=`）与单页正文、引用、质量问题（下架的页面对其他员工是 404） |
| `GET /versions/:id/original` | 下载原件（经会话鉴权，带 `nosniff`；已撤回材料的原件只对上传者与管理员开放，其余为 404） |
| `POST /answers` | 提问：按问题在**所在库**内路由到已发布页面，生成带脚注引用的回答（请求体带 `baseId`）；每条引用带 `pageSlug`、`documentId`、`versionId`、材料标题与文件名，可跳回依据页与下载原件；有引用时返回 200，无覆盖时返回 422 `knowledge_no_coverage` 与中文 `message`，库不存在时返回 404 `knowledge_base_not_found` |
| `GET /answers` | 本人的问答记录：按 `created_at` 倒序分页（`?baseId=`、`?limit=`、`?offset=`，返回 `pagination.nextOffset`），每条含问题、回答正文、引用、覆盖度与时效；引用在读取时联表补出材料信息，可跳回依据页、材料与原件 |

材料详情 `GET /documents/:id` 对可读取的 Markdown 版本额外返回 `bodyMd`（UTF-8 原件正文），供已批准员工在详情页直接阅读；其他格式仍只保留元数据与原件下载。知识页详情 `GET /pages/:slug` 返回同库已发布页面的 `related` 标题与 slug，页面据此把历史正文里的短 slug／完整 slug 链接解析为标题与有效地址；来源计数按详情实际返回的引用条数显示。已发布目标存在时，历史遗留的 `related-target-missing` 误报不会在详情继续展示；库中确实不存在的目标仍报告。

排查问答接口 404 时先看响应体的 `error`：`knowledge_base_not_found` 是库号问题，`not_found` 是路由／部署版本问题；无覆盖与路由缺失分别返回不同状态。员工页把问答错误显示在提问表单下方。生产发布后应分别用已发布页面覆盖的问题和无覆盖的问题验收；只检查健康接口不能证明问答可用。

## 4. 构建流程

队列 `membership.knowledge`（pg-boss，单并发，不自动重试），每个阶段都留检查点：

1. `extracting`：按字节判定格式（PDF／DOCX／Markdown），抽取文本并保留页／章节锚点；PPT/PPTX 须先转换为 PDF，已有待处理的 PPTX 版本在提取前标记为不可用。抽不出文字的原件记 `unavailable`，不生成页面。超出单次构建上限（`MAX_EXTRACTED_CHARS`，60,000 字符）时按节截取，节内过长时保留预算内的非空前缀；截取后仍无文本则构建以 `knowledge_text_empty` 失败，不调用模型。
2. `compiling`：编译者在独立上下文中把材料编译成结构化草稿（页面、观点分布、时间线、来源、问答、框架、监测指标）。
3. `auditing`：复核者在另一个独立上下文中对原文核实，只能**撤回**条目或把归因降为「未知」，不能新增观点；结论为 `fail` 时整批不发布。复核给出的下标指向它读到的草稿：归因先落在原条目上，撤回再按原下标批量执行，越界与重复的修正被忽略并记为质量问题。复核没有给出平台认识的结论（缺结论、类型不对、结论不认识）时，这一轮复核不算发生：构建以 `knowledge_model_output_invalid` 失败，不发布任何页面，也不写成功事件。
4. `linting`：机器检查（归因可识别、立场词表、时间锚、时间线倒序、覆盖度口径、Related Pages 指向）；`P0` 问题不发布。
5. `publishing`：一个事务内写入本份材料的贡献、聚合后的页面新修订、引用锚点和质量问题记录。旧修订继续可读。

- **发布围栏**：发布事务按固定顺序锁材料与任务（先材料后任务），并核对材料仍为 `active`、任务仍为 `running`、租约令牌属于当前 worker 且未过期；任一项不满足就不写页面也不写成功事件（错误码 `knowledge_lease_lost`／`knowledge_document_withdrawn`）。每个阶段的 `UPDATE` 影响 0 行即停止后续工作。同一材料的旧版本构建不得覆盖新版本已发布的内容（错误码 `knowledge_publish_stale`）。
- **多材料聚合**：每份材料版本对同一标的（`target_key`）保存一份结构化贡献（`member_wiki_contributions`），当前页面由该标的所有有效贡献聚合而成；更新一份材料只替换它自己那份贡献，其余材料与版本不受影响。页面按 `target_key` 加锁，并发发布的两份材料都在页面上。
- 重跑：`membership.knowledge-recover` 每 5 分钟把仍处于 `active` 的材料所属、租约过期的构建重新入队；`POST /tasks/:id/retry` 由上传者手动重跑，材料已撤回时拒绝。worker 领取排队任务也核对材料仍为 `active`，旧队列消息不能触发模型调用。自动恢复与手动重试共用最多 5 次领取预算；达到上限时任务转 `failed`，保留 `knowledge_retry_exhausted` 原因，不再入队。
- 上传与手动重试在同一员工锁下共用准入：同时最多 2 个排队或运行任务，滚动一小时最多 10 次新任务或手动重试。已准入的重试写审计事件供窗口计数；额度不足返回 429，任务仍为失败且不入队。已撤回材料的旧 SHA 保留供审计，不参与活跃库查重；相同字节可重新上传为新材料和新任务。
- 重跑从上次成功的检查点继续：模型不可用等临时失败会重新跑那一步；**确定性的质量失败**（复核不通过、结构检查出现 P0）重跑结果相同，需要新材料版本或修正规则。
- 上传材料只作数据：正文里的指令不改变规则，构建过程不执行材料中的任何程序。
- **模型回答的归一**：两次模型调用的回答先按平台自己的口径读一遍（`knowledge/normalize.ts`），再交给 schema 校验。页面类型归到平台已有的四种（`view`／`query`／`concept`／`monitor`），来源的 `organization`／`author` 别名读作机构与作者，立场的 `author`／`org` 别名读作分析师与机构，模型没写的数组按空数组处理。归一只做机械改写，不补造事实；改写后仍读不出的字段由 lint 显示为质量问题，而不是让整批构建失败。三处不许猜：
  - **日期**：只有写全了年、月、日且日历上真有这一天的写法（`2026年6月20日`、`2026/06/20`、`20260620`、`2026-06-20`）才读成 `YYYY-MM-DD`；只写到年或年月的（`2026年6月`、`2026`）记「未知」，不补成当月第一天；日历上没有的日子（`2026-02-30`、`2025-02-29`）不是日期，记「未知」，也不进时间线和时效。
  - **立场与引用**：模型没写评级就不写（不补「中性」），没写来源就不写（不借第一条来源）；两者都由 lint 记为质量问题（`stance-missing`／`source-missing`），页面显示「未知」。
  - **根结构**：编译者给的不是草稿（没有 `pages`、`pages` 不是列表、只有 `error` 对象）时构建在 `compiling` 阶段失败（`knowledge_model_output_invalid`），发布事务不开始，已发布版本继续可读；只有明确写 `pages: []` 才是空构建。
- **复核的结论**：只认 `pass`／`pass_with_issues`／`fail` 三种结论（大小写和分隔符差异不区分，`failed` 读作 `fail`）；缺结论、类型不对或不认识的结论一律按解析失败处理，构建不发布。
- **调用形状**：编译与复核各一次调用，输出上限分别为 12,000 与 8,000 tokens（`knowledge/compile.ts`），提示词版本 `wiki-builder-1c`／`wiki-auditor-1e`。提示词里保留「只返回一个 JSON 对象」一句：模型走 `response_format=json_object`，该模式要求提示词中出现 json，改写提示词时不要删这一句。

## 5. 存储、容量与备份

- **原件按字节存在数据库里**（`member_wiki_document_versions.body`），不放公开静态目录；下载一律经 `GET /versions/:id/original` 鉴权。
- 单文件上限默认 10 MB（`MEMBER_KNOWLEDGE_MAX_FILE_MB`，最大 20 MB）。按 20 名员工、人均每周 5 份材料估算，一年的原件体积在 1 GB 量级；数据库备份体积随之增长，纳入每日备份即可。
- 备份：数据库每日 `pg_dump` 已覆盖原件、提取文本、知识页、修订、引用与审计。**备份不按一周清理**（与专家任务的 7 天清理不同）。
- 迁移到对象存储（如需）时，把 `body` 换成对象存储键并保留校验和，页面与接口不变；本版本尚未实现。

## 6. 保留与撤回

| 数据 | 保留 |
|---|---|
| 原件、提取文本、知识页、修订、引用、审计 | 长期保留，不自动清理 |
| 失败的构建任务与其错误 | 随任务长期保留；页面显示失败原因 |
| 问答记录 | 长期保留，供复盘 |

- 撤回：上传者或管理员在材料列表点「撤回」，页面先说明后果（该材料及其生成的知识页将从共享库下架，且不可恢复），确认后执行；原件字节保留在库中以备审计，但页面不再展示与引用。
- 撤回在有聚合的标的上只影响该材料自己的贡献：页面按剩下的有效贡献重新聚合（新的修订），只有当页面再无其他材料支撑时才下架该页。撤回后的原件与页面只对上传者与管理员可见（其余员工得到 404）。
- 彻底删除（连原件字节一并删除）目前**没有**自助入口，需要管理员按运维流程在库内操作；如实现，须同步更新本手册与需求基线。

## 7. 监控与费用

- 队列积压与失败：看 `member_wiki_tasks` 中 `state IN ('queued','running')` 与 `state='failed'` 的数量，页面上直接显示。
- 模型调用与费用：每次构建 2 次（编译、复核），每次问答 1 次；按现有模型回执在后台「运行」页查看用量与费用。
- 存储用量：看 `member_wiki_document_versions` 的字节总和与备份体积。

## 8. 环境变量

| 变量 | 默认 | 用途 |
|---|---|---|
| `MEMBER_KNOWLEDGE_MAX_FILE_MB` | 10 | 单个上传材料的大小上限（MB，最大 20） |

模型调用仍受 `MODEL_CALLS_ENABLED` 控制；关闭时构建与问答会失败并给出可重试的提示。

## 9. 部署与回退

1. 合并后按常规发布流程执行 `npm run db:migrate`（新增 19 条迁移），再发布 api 与 worker。
2. worker 启动后 `membership.knowledge` 队列与 `membership.knowledge-recover` 定时任务随站点模块自动注册。
3. 回退：回退代码版本并保留新表（不影响旧功能）；如需回退数据结构，另写追加迁移删除新表（历史数据留在 `member_wiki_*` 表中）。

## 10. 与本地投研 wiki 工具的环境差异

平台实现参考了本地 `investment-wiki-builder` / `investment-wiki-answer` 的**业务规则**（归因三要素、共识与分歧并列、边际变化、时间线、时效三档、可溯源脚注、构建与复核分离、lint/audit），但实现形态不同，私有仓库的源码、提示词与内部样例**不进入本公开仓库**：

| 维度 | 本地工具 | 本平台 |
|---|---|---|
| 运行形态 | 单机目录 + Python + git 提交 | 常驻服务：api + worker + PostgreSQL 队列 |
| 存储 | `raw/`、`wiki/` 下的 Markdown 文件 | 数据库表（原件字节、版本、材料贡献、页面修订、引用、质量问题、审计） |
| 角色分离 | 人工派发独立上下文的 Builder 与 Auditor 子 agent | 两次独立模型调用（编译、复核），复核者只能撤回或降级归因 |
| 质量检查 | `wiki.py lint` / `audit` 命令 | 独立复核 + 平台内的机器检查（同一批规则：归因、时间锚、词表、覆盖度、指向） |
| 检索 | 读各库的 `INDEX.md` 路由 | 按库分开的页面集合，按关键词与字元重合度在所问之库内路由到页面 |
| 多材料 | 同一标的多份材料合成一篇 Markdown | 同一标的的多份材料各留一份贡献，当前页面由有效贡献聚合而成 |
| 保留 | 本地目录自行管理 | 长期保留，不适用专家任务 7 天清理（见 §6） |

平台首版未实现：多库发现与锁定、git 历史分片与回滚、待决队列（PENDING）、概念／框架的家族关系管理、定时 lint 与看板。

## 11. 已知限制与未验证事项

- 问答只覆盖**已发布**的知识页；构建中的材料不参与问答。
- 问答只接受模型给出的**引用 ID**：模型只能引用本轮给出的已发布修订的引用锚点，服务端按 ID 还原归因、覆盖范围与时效，引用不上的一律丢弃；一条可核对引用都没有的回答按 `knowledge_answer_unverified` 拒给。
- 问答的脚注编号由本轮给出：平台为本轮每条可用引用编一个 `footnote` 数字，模型在正文写 `[^1]` 这样的角标，并在 `citations` 里写回这个编号、该引用的 `citationId` 与页面标识。模型改用页面自己的来源编号（`sourceLabel`，如 `S1`）作角标也能核对；把另一个来源的编号写进来则整条回答拒给。
- 页面标识写短了（截断）仍按同页处理，引用 ID 说了算；完全不相干的页面名照旧拒给。
- 回答核不上时接口返回 **422** `knowledge_answer_unverified`（请求已被理解，是回答没通过核对），不是网关错误；模型调不动才回 502 `knowledge_answer_failed`。核不上的回答会释放模型回执，下次提问重新调用模型，不会把同一份核不上的回答再端一次。库里没有覆盖仍是 422 `knowledge_no_coverage`。
- 问答记录（`GET /answers`）读取时把引用补回材料：先按回答记下的 `versionId`，再按引用行 `citationId`，最后按该页当前唯一的一条来源（页面有多条来源时不猜，材料留空）。缺失的分析师／机构／日期保持空，页面显示「未知」。
- 页面检索是关键词与字元重合度路由（中文按二字组合），不是向量检索；标的别名与同义词可能影响命中。
- 页面的 `coverage.reports` 统计的是该页引用的**来源数**（材料内的来源为单位），不是上传份数；问答的 `coverage.reports` 统计的是本次实际用到的**材料份数**。
- 同一标的的页面由 `target_key`（页面类型＋标的类型＋标的名称）归并；编译器把同一标的写成不同 slug 时仍归到同一页，页面的 slug 取首次发布时的那个。归并在**库内**进行（见 §2.1）。
- 扫描件 PDF 没有文字层，只会被标记为「未能提取文本」，不做 OCR。
- 真实中文 PDF 的抽取效果、真实研报的页面质量、两名员工共用一个共享库的实际情况，均需在真实环境试用后确认。
- 多个知识库的模型尚未在真实环境试用：一个库里的材料是否会被编译器写成与另一个库相同的 slug、跨库引用是否会被机器检查拦下，都还没有真实材料可验证（见 §13）。


## 12. 复审补充的发布与问答边界

- 一份材料可同时贡献多个知识页；新版成功时一次替换该材料的全部旧贡献，重建不再出现的目标页面，其他材料的贡献保持不变。新构建失败不会下架旧发布。
- 发布和撤回按排序后的目标集合取得事务锁，避免多目标构建交叉锁定；成功发布的版本（包括不产生页面的版本）都阻止旧版本随后覆盖当前状态。
- 问答只接受本次路由提供的引用 ID 与脚注标签；脚注标签可以是本轮的编号或页面自己的来源编号，部分无效或未绑定脚注会拒绝整条回答。覆盖与时效按实际引用计算，当前页面包含新材料不代表被引用的旧材料也是当前观点。
- 模型响应期间若依据页更新或材料撤回，回答保存前再次检查相同修订及共享状态；变化时返回 409，员工重新提问即可。不会保存已经失效的回答。
- **问答可跳回依据**：每条引用除脚注标签与依据页外，还带 `documentId`（材料）与 `versionId`（原件版本），页面据此给出材料页与原件下载两个入口；材料缺失的元数据显示「未知」，不补造。
- **构建列表分页**：`GET /tasks` 按 `limit`（1–100，默认 50）与 `offset` 取一页，返回 `hasMore` 与 `nextOffset`；列表不再被固定 100 条截断。
- 复审与回归记录见 [PR #34 复审日志](logs/2026-10-24-P5-pr34-review.md)。真实模型语义质量及 P5-02～P5-04 的真实员工验收仍待执行。

## 13. 多个知识库（Issue #36）的落地边界

- **库本身**：一个库是一行 `member_wiki_bases`；库号既是它的主键，也是它页面前缀的一部分。默认库 `shared` 的名称是「知识库示例」，它在第一次读取库列表时写入（`ensureDefaultBase`），因此不需要在迁移里插数据。默认库归平台所有：每次读取库列表时 `ensureDefaultBase` 都会把它改回平台当前的名称与说明（改版发布后自动改名），员工自建的库不改名。
- **新增库**：已批准员工在「知识库」页头点「+ 新增知识库」创建；名称 2–80 字、说明 ≤200 字；同时存在的库上限 20 个（`MAX_BASES`），达到上限时接口返回 `knowledge_base_limit_reached`。库没有逐条审核，与材料入库一致。
- **材料与页面**：上传时带 `baseId`（缺省为共享库）；构建时页面按库写入，页面的 `target_key` 与 `slug` 带库号前缀（共享库除外，见 §2.1）。页面上的 Related Pages 指向也按本库前缀改写，机器检查只看本库的页面。
- **撤回**：撤回材料只影响它所在库的页面；其他库的同名页面不受影响。
- **问答**：提问带 `baseId`，只在该库的已发布页面里路由；库里没有覆盖时返回 `knowledge_no_coverage`。
- **未验证**：多库的真实材料与真实模型调用尚未试跑；库之间的权限模型目前是「同一批已批准员工都能看全部库」，还没有做到按库授权（见 §11）。
