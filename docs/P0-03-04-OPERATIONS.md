# P0-03 / P0-04 外部验收手册

本手册把个人微信双用户试投和 `ai-work` 只读盘点整理成可复核步骤。手册和代码合并均不代表真实渠道、服务器或备份已验收；结果只有在执行后写入脱敏日志，才可更新 `docs/IMPLEMENTATION.md`。

截至 2026-10-22：Hermes Weixin/iLink 网关已在火山云部署，单个 iLink bot 身份完成扫码并已连接；私聊使用配对审批，群聊关闭。尚未执行两名员工的原生私聊、分别定向投递和 D+1 跨日送达验收，因此 P0-03 仍未完成。服务器已完成只读盘点；用户决定服务器整体供新平台使用，旧应用保持不动，因此 P0-04 操作边界已确认并完成。旧版异地备份、恢复演练及旧应用资源清理均不属于 P0-04 完成条件。部署证据见[Hermes 网关部署日志](logs/2026-10-22-P4-hermes-gateway.md)。

## P0-03：双用户绑定、主动投递与跨日送达

### 开始前的闸门

1. 取得两名内部测试用户的明确参与同意，测试记录只用 `A`、`B` 代称，不记录姓名、微信号、完整收件人 ID、二维码或绑定码。
2. 在隔离的试用环境使用锁定版本的 [Hermes 官方 Weixin/iLink 适配器](https://github.com/NousResearch/hermes-agent/blob/ebc9960b9d42e11e35ddbb6f0918cc163f739eb1/website/docs/user-guide/messaging/weixin.md)。运行 `hermes gateway setup` 扫码连接一个 iLink bot 身份，再运行 `hermes gateway`；A、B 各自先向该 bot 发私聊。官方适配器通过长轮询直接收发，无需另建微信协议网关或公开 webhook。按官方说明限制允许私聊的用户。
3. 首轮只核验 Hermes 原生渠道的双用户定向发送和跨日主动投递，不要求平台 bridge，也不启用本平台的 `P3_GP_SYNC_ENABLED`、`P3_NOTIFICATIONS_ENABLED`、`P3_DELIVERY_ENABLED`。网页账号自行绑定和平台 outbox 联调见下文；生产开关仍按 `docs/P3-OPERATIONS.md` 的闸门管理。
4. 预先约定北京时间试投日期、观察窗口和停止联系人；正文使用固定的无敏感测试文本及唯一试投编号，不携带新闻、客户、项目或个人信息。

任一闸门不满足时停止试投并记录阻碍，不以生产开关临时开放来绕过隔离或授权要求。

### 最小步骤

| 时点 | 操作 | 通过证据 |
|---|---|---|
| D0 | 确认同一个 iLink bot 与网关在线。A、B 各自向 bot 发起私聊；从 Hermes 入站事件取得两名不同的收件人 ID，按官方策略加入允许名单。 | Hermes 分别收到 A、B 的私聊，能识别两名不同的收件人。日志仅保留代称和脱敏关联 ID。 |
| D0 | 使用 Hermes 内置的定向发送能力，分别向 A、B 投递不同编号的安全测试消息；检查 Hermes 任务及发送结果，再由两位用户分别确认实际收到的时间和内容编号。 | A 只收到 A 的编号，B 只收到 B 的编号；两位用户确认收到。接口受理或任务完成本身不算用户送达证据。 |
| D+1 | 在至少跨过一个北京时间自然日后，A、B 均不先向 bot 发消息；再次通过 Hermes 原生能力分别主动投递，并记录发送结果及用户确认。 | 两位用户无需重新发起会话即可收到各自消息；无错收、重复或串号。 |
| 故障恢复（若 D+1 失败） | 先记录原始失败分类；如渠道提示会话过期，再由相应用户主动私聊一次，随后只重试一条新的唯一编号消息。 | 明确区分“跨日主动投递失败”和“用户重新发起后恢复”；恢复结果不能把 D+1 验收改记为通过。 |

原生定向发送可使用 [Hermes 的无模型 cron 脚本任务](https://github.com/NousResearch/hermes-agent/blob/ebc9960b9d42e11e35ddbb6f0918cc163f739eb1/website/docs/user-guide/features/cron.md)：脚本放在 Hermes 的 scripts 目录，只输出固定的无敏感试投编号，为 A、B 分别建立 `--no-agent --script ... --deliver "weixin:<收件人 ID>"` 任务。Hermes [目标语法](https://github.com/NousResearch/hermes-agent/blob/ebc9960b9d42e11e35ddbb6f0918cc163f739eb1/website/docs/developer-guide/cron-internals.md)支持向具体微信用户定向投递；不要用单一默认 home channel 代替双用户测试。网关重启后的恢复测试可在独立受控窗口追加，不要为此重启共享生产网关。

**网页账号联调：**原生试投确认渠道可行后，A、B 还须分别在 `/settings/notifications` 完成网页账号绑定、订阅、解绑与重新绑定，并核对平台 outbox 对应的收件人和送达反馈。这一层需要本平台与 Hermes 的连接接口，但应复用 Hermes 已有 Weixin 适配器，不重写 iLink 协议；它属于 P3-04 的完整产品验收。平台的 `accepted` 只表示接口受理。

## P0-04：`ai-work` 只读资源与边界盘点

**用户决策（2026-10-22）：** 火山云服务器整体供新平台使用，旧应用保持原样，不对旧应用执行停止、迁移或清理。结合已完成的只读现场盘点，P0-04 边界已明确并完成；不必为了 P0-04 再逐个确认旧应用资源所有权。此决定不代表已经执行服务器资源变更。

### 当前可确认的基线

- `docs/PLAN.md` 的 2026-10-21 记录称，当时 SSH 可连接、实例运行 Ubuntu、Nginx 活跃且存在 `ai-work-mvp` 站点配置。这是历史基线，本轮没有重新验证。
- 本轮任务执行环境的网络策略为受限模式，VPN 未配置，TCP 授权域名和 IP 范围为空，也没有外发身份。它说明当前任务环境没有到目标实例的网络路径，不能据此推断实例本身的状态。
- 仓库的 `docker-compose.yml` 静态定义了 `db`、`setup`、`api`、`worker`、`web`，以及可选的 `caddy`；声明了 `db`、`data`、`caddy` 卷。`web` 映射 `${PORT:-3000}:3000`，可选 Caddy 映射 80/443；Compose 未声明数据库宿主机端口，也没有 Hermes/iLink 服务。它只描述新平台的期望配置，不是 `ai-work` 的实时清单。

### 连接及采集要求

1. 通过受控连接能力提供 `ai-work` 的只读 SSH 入口或身份别名，并确保执行环境获得明确的 TCP 授权。不要把私钥、密码或完整连接串粘贴到 PR、日志或聊天记录。
2. 在执行前记录操作者、北京时间、连接目标的脱敏别名和只读授权来源。直接使用已授权的只读账号运行命令；如果权限不足，就记录缺项，不要临时提权或修改远程状态。
3. 以下结果只留在受限访问的运维记录中。公开仓库仅记录脱敏后的资源类别、归属结论、验证日期和未解决项。不得保存完整主机名、IP、私人目录、`.env`、`.config`、进程环境、密钥内容或原始 Nginx 配置。

### 只读采集清单

| 范围 | 只读检查 | 必须记录的结论 |
|---|---|---|
| 系统与容量 | `uname -sr`、`nproc`、`free -h`、`df -hT`、`lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS` | 系统版本、CPU/内存/磁盘容量和使用率；挂载点在公开记录中脱敏。 |
| 端口与服务 | `ss -ltnup`、`systemctl --no-pager --type=service --state=running` | 监听端口、服务类别和归属；逐项标记 `ai-work-mvp`、共享平台或其他服务、负责人、证据日期。 |
| 容器与存储 | `docker compose ls --all`、`docker ps -a --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'`、`docker volume ls`、`docker network ls` | Compose 项目、容器/镜像、端口、卷和网络；对每个旧应用资源确认所有者与依赖方。 |
| 挂载归属 | 对选定容器使用 `docker inspect --format '{{.Name}} {{range .Mounts}}{{.Source}} -> {{.Destination}}; {{end}}' <容器 ID>` | 仅提取挂载，不读取完整 inspect 输出（其中可能有环境变量或敏感配置）；完整路径不进入公开日志。 |
| Nginx 与入口 | 在服务器私有会话中检查 `nginx -T` 输出及证书元数据 | 记录站点配置归属、监听端口、上游类别、证书有效期及与其他服务的关系；不复制完整配置或证书内容。 |
| 数据库与文件 | 只读确认实例/容器、数据目录或卷、所属应用、备份任务与最近成功时间 | 区分旧应用、共享或其他服务；记录当前新平台备份策略，不查询或复制业务数据。旧版留档已归档，不要求旧版恢复证明。 |
| `ai-work-mvp` 边界 | 将旧站点配置、相关容器、挂载、数据库、文件路径逐项与其他服务交叉核对 | 只有证据明确属于旧应用且业务负责人确认的资源才可标为候选清理；共享或归属不明资源一律保留。 |
| 备份前置 | 旧版 `ai-work-mvp` 已按用户决定同机归档留存；不要求旧版异地备份或恢复演练。新平台备份按其运维策略另行验收。 | P0-04 记录盘点事实；退役组件前确认共享服务影响，不把旧版恢复证明作为前置。 |

`nginx -T`、磁盘/挂载和容器元数据可能暴露内部路径或站点信息，只能在受控终端查看并人工脱敏。不要运行 `docker compose down`、`stop`、`rm`、`volume prune`、删除/迁移文件、数据库写入、重启服务或证书操作；本任务不授权清理服务器。
