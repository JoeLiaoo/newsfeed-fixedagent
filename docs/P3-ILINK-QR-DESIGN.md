# P3-04：个人微信扫码接入与受限主动推送（代码实施及部署后验收）

决策日期：2026-10-22。用户确认：这是 side project，不使用企业微信/需要组织审批的渠道；允许员工在会话窗口失效后**主动向机器人发一条消息**，恢复后续定向推送。无需限制每个员工是否共用同一个 bot。对外体验优先：登录网站 → 扫描专属二维码 → 微信端确认 → 网站自动显示绑定成功 → 根据网站兴趣及订阅设置收消息。

**实现状态：代码经 [PR #15](https://github.com/JoeLiaoo/newsfeed-fixedagent/pull/15) 合并到 `main`（`acef3866367d`），并已随 `main` 提交 `5031e2c04dec382263d05b38484b0cfaabeaa15b` 部署；功能开关已按用户指示启用，仍待双用户真机验收。** PR #15 已移除静态联系人二维码 + 手动验证码 + 网页确认的旧流程；新增平台会话绑定、iLink 二维码生成和轮询、原子身份绑定、AES-256-GCM Bot token 与 cursor 加密存储、多账号收件箱轮询、按收件人发送、会话互动恢复状态和自动化 mock/数据库测试。独立 iLink 账号的主动推送不再通过旧 Hermes 插件的单例 `_adapter`，旧插件仅兼容历史通道。生产迁移 `0152`–`0155` 已应用；`P3_ILINK_CREDENTIAL_KEY` 已安全配置，`P3_ILINK_BINDING_ENABLED`、`P3_GP_SYNC_ENABLED`、`P3_NOTIFICATIONS_ENABLED`、`P3_DELIVERY_ENABLED` 均为 true。启用时有 0 个 active 微信绑定、0 个 iLink 账号、0 条通知 outbox、0 个 GP watchlist/active GP，因此暂无实际微信投递或 GP 同步；P3-04 仍未勾选。

**本轮修复（记录见[服务端确认绑定日志](logs/2026-10-22-P3-04-server-side-binding.md)）：** 2026-10-22 生产实测发现员工扫码后服务器没有记录绑定（`member_ilink_logins` 一直 `status=wait`），原因是网页在标签页不可见时停止轮询，而服务器只在网页请求状态时才去问渠道。代码已改为由 worker 定时确认扫码会话、网页回到前台立即查询、渠道失败返回可区分的错误状态，并在收到首条入站消息时回一句连接确认；该版本尚未部署，线上行为以上一次发布为准。

**范围说明：** 本轮完成网页扫码绑定和订阅推送通道。扫码得到的独立 iLink Bot 可以收取用户互动以刷新推送上下文，但**这些 Bot 的普通聊天消息暂不会被交给 Hermes Agent**；原 Hermes 聊天网关单独保留，不能把“推送 Bot 可绑定”描述为“多 Bot Hermes AI 对话已接通”。若后续需要每个员工在同一 Bot 内与 Hermes 直接对话，应另外增加租户隔离的 Hermes ingress/pairing 联调并独立验收。

## 上游事实和不能推断的能力

- 腾讯维护的 [openclaw-weixin 协议说明](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol_zh_CN.md)显示：先 `POST /ilink/bot/get_bot_qrcode?bot_type=3` 获取二维码，再 `GET /ilink/bot/get_qrcode_status` 轮询；确认时可能返回 `ilink_user_id`（扫码用户）、`ilink_bot_id`、`bot_token`、`baseurl`。可能出现 `need_verifycode` / `expired` / `binded_redirect`。**平台不能保证每次扫码都免除微信端额外验证**，但不得再要求网页绑定码或人工确认。
- 腾讯的 [openclaw-weixin 实现](https://github.com/Tencent/openclaw-weixin/blob/main/src/auth/login-qr.ts)提供 QR login 和多账号管理参考。该二维码是**给扫码者的 bot 登录/授权**，与给多人添加同一 bot 联系人的静态二维码不同。需要每位网站用户独立绑定扫码登录结果，不能把 `ilink_user_id` 当成由浏览器自由提交的值。
- 当前锁定版 [Hermes Weixin 文档](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/weixin.md)面向单个 `WEIXIN_ACCOUNT_ID`；**多 bot 汇聚/多 profile 的实际运行方式需要原型验证**，不能把 OpenClaw 的多账号支持直接当成 Hermes 已支持。
- [第三方实测](https://cloud.tencent.com/developer/article/2646635)提到主动推送可能受用户主动发消息后的时间窗口和发送次数限制，例如约 24 小时 / 10 条；这是经验观察，**不是稳定的官方配额承诺**。超出窗口不得继续盲目重发，不能承诺每天必达。
- iLink 返回的 `ilink_user_id` 是否可以**直接作为同一 bot 的有效主动投递 `to_user_id`**，以及账号/会话刷新后的送达行为，须以真实双账号端到端测试确认。未通过前，不能把扫码成功等同于具备推送能力。

## 安全与身份模型

1. 只允许 `member_users.status='active'` 且当前登录会话仍有效的用户发起扫码；服务器为其建立随机、短期、一次性的扫码会话（例如 5 分钟），存当前网页登录会话的 token 哈希、`user_id`、到期时间和状态。重复请求和并发扫码有明确冲突/替换规则，不允许重放旧二维码。网页不传入微信收件人 ID。
2. 扫码过程由可信后端调用 iLink 的二维码与状态 API；`ilink_user_id`、`ilink_bot_id`、`bot_token` 只从后端经 HTTPS 获取的确认结果读取。确认时再次在数据库事务内验证该平台用户仍为 active、原网站登录会话有效且扫码请求未过期/未使用，然后一次性写入 `user_id ↔ ilink_user_id ↔ ilink_bot_id`。不允许同一 iLink 用户被静默绑定到不同平台账号。
3. `bot_token` 仅保留于受限凭据存储中并加密，数据库以不泄漏密钥的标识引用；任何 API、日志、PR、浏览器响应都不返回 token、二维码密钥或完整微信身份；解绑要撤销本地令牌/会话使用并清空关联，供应商侧撤权能力另行核对。
4. 网页只轮询自己的非敏感扫码状态（等待/需微信端操作/成功/过期）；真正完成绑定无需第二次网页确认。普通 Agent 聊天的 Hermes pairing / allowlist 不得被绑定或订阅自动授予。
5. 每个绑定必须有独立 `channel_account_id` + `recipient_id`；出站按两者选择隔离的账号凭据与 iLink transport，不能使用一个全局 `_adapter` 把两名用户混投。每个 bot token 同时只允许一个轮询进程。

## 投递规则（用户同意的降级）

- News 和 GP 订阅默认开启，可独立退订；兴趣仍来自网站，出站使用现有持久化 outbox 的用户隔离、去重和幂等。
- 首次收到扫码成功回执时显示「已绑定」。只有首条真实消息发送和用户确认后，才展示「推送可用」；仅收到接口 `accepted` 不意味着微信实际送达。
- 当渠道返回明确的会话窗口失效/需用户互动错误时，进入 `needs_interaction`（需用户在微信向 bot 发一条消息），**不要自动视为用户解除绑定或清除其订阅**。渠道登录凭据过期才进入 `requires_rebind`（需重新扫码）；二者必须分开。非确定失败维持 `unknown` 并阻止盲重试。
- 员工从微信发送恢复消息后，仅由可信渠道更新活跃窗口；恢复后重发应该产生新的幂等动作，不能无条件重放 `unknown`。
- 扫码确认由服务端自己完成：worker 定时查询未过期的扫码会话，确认后写入绑定，网页是否在前台不影响结果；网页回到前台时立即拉取一次状态并显示已有的「已绑定」状态。每次生成二维码时都会产生不同的加密 `qr_secret`，页面与 worker 的轮询结果及绑定事务只可更新读取时的那一代扫码；旧查询返回后不得修改新二维码。渠道查询失败时状态接口返回可区分的错误，网页显示一行失败状态并允许重新生成二维码，不把失败显示成「等待中」。
- 收到某账号第一条入站消息（或会话从 `needs_interaction` 恢复）时，只回一句「已连接，之后会在这里推送。」，每个账号一次；这条确认与其它渠道发送一样受 `P3_DELIVERY_ENABLED` 控制，不做其它自由聊天回复。
- 如果每日总条数受限，尽可能控制长消息分片数量；不得假定超长内容免费或可突破额度。暂停期间不积累无限待发通知；明确对过期日的丢弃/手动补发规则。

## 实施顺序与验收门槛

### A. 自动化代码验证（合并前）

- 使用隔离的 PostgreSQL 和模拟腾讯 iLink API，验证 **两个不同 active 网站账号** 请求短期二维码、扫码回执、自动绑定、重复扫码与跨账号争用；未获批准账号不能登录绑定。真实手机扫码放在部署后。
- 使用独立的 iLink 多账号收发层（不是 Hermes 的单实例 `_adapter`），自动化测试验证两个 Bot 的 Token、游标、上下文令牌与收件人不会串号；**真实微信环境的持续连接与送达仍待部署后证明**。
- 自动化覆盖定向推送、过期状态分类、用户新消息恢复、解绑、退订与幂等；在部署后使用两位自愿员工进行跨日无互动、用户侧送达、重复消息和窗口恢复真机验收，脱敏记录实际结果。
- 如无法取得扫码者的有效主动投递目标或多账号稳定发送，先停止开发该实现并重新评估通道，而不是展示假绑定成功。

### B. 已实现的工程交付（合并前）

- 服务端已实现 `/weixin/start`（短期专属二维码）、`/weixin/status`（从 iLink 回执自动绑定）、`/weixin/verify`（微信侧安全验证时使用）和 `/weixin/unbind`；旧手输绑定码和 `/weixin/confirm` 已停用。新增迁移 `0152`–`0155`。
- 新增 `modules/membership/notifications/ilink.ts`（协议与凭据加密）、`inbox.ts`（按 Bot 独立轮询和恢复互动窗口），出站由 `outbox.ts` 按账号选择对应身份，原 Hermes 单例仅供历史兼容。网页显示扫码入口、状态、恢复提示及两类订阅。
- 扫码确认不再依赖网页持续轮询：worker 注册 `membership.ilink-scan`，对未过期的扫码会话自行查询渠道状态，确认后调用与网页相同的落库函数（`notifications/binding.ts`），网页轮询与后台确认同时到达时只保留一条绑定；过期会话标记 `expired`。扫码结果写入按 `qr_secret` 比较当前代际，不依赖同一网页登录会话的哈希区分前后两个二维码。网页在标签页重新可见时立即查询一次，隐藏时降频继续查询。渠道失败时 `/weixin/status` 返回 502 与 `status=error`，网页显示失败并允许重新生成二维码。首条入站消息的连接确认由 `member_ilink_accounts.greeted_at` 记录，每个账号一次（迁移 `0156`）。
- 针对性测试覆盖二维码会话隔离、审批前禁止绑定、Bot 身份冲突、各用户令牌/上下文不串号、各自接收订阅及解绑；持续时间窗口、上游协议具体返回格式和真实送达未做手机端试验。
- 检查版本必须以 PR head CI 为准；必须区分测试模拟与真实渠道验证。文档不能将这部分写成已完成 P3-04 业务验收。

### C. 合并部署后验收（尚未执行）

- 新版本部署后，先仅配置 `P3_ILINK_CREDENTIAL_KEY` 并按受控试用条件开启 `P3_ILINK_BINDING_ENABLED`；其余三个 P3 开关不随合并自动开启。
- 两个**已经管理员审核的真实网站账号**分别扫码确认；验证无网页绑定码、自动变更绑定状态、本人消息正确恢复独立会话、不同订阅和赛道不会串投。
- 从服务端与两台个人微信终端同时核对真实回执，覆盖跨日、窗口过期后用户主动消息恢复、重复/未知结果、退订/解绑以及授权信息的安全性。
- 正式投递启用需另行通过数据源授权、P3 验收及 P4 运维条件；保留回滚办法。普通聊天暂不接入独立 iLink Bot 的 Hermes Agent，不得将其描述为已完成。

## 非目标

不引入企业微信、公司审批、共享机器人静态联系人二维码、网页人工绑定码或网页二次确认。不承诺 iLink 24 小时之后也可以完全无人互动地推送。

## 部署后的最短操作清单

1. 发布 PR 对应提交并执行增量迁移。保留原 Hermes 服务与旧部署回滚版本，不复用 Hermes 网关单账号登录 Token。
2. 在 API 和 worker 共同可读的受保护环境配置 `P3_ILINK_CREDENTIAL_KEY`（`openssl rand -hex 32`），确保备份/后续重部署使用**同一个**密钥。先仅打开 `P3_ILINK_BINDING_ENABLED=true`，保持三个 `P3_..._ENABLED=false`。密钥值绝不进入 Git 或公开日志。
3. 使用两个已批准网站账号分别点击「扫码绑定微信」；生成二维码后浏览器直接跳转到微信官方页面，不在站内嵌入二维码。扫描并在微信内确认后，返回平台「绑定微信」页查看绑定状态；页面会恢复轮询，后台 worker 也会继续确认扫码。出现 `need_verifycode` 时完成微信自身的额外安全验证。网页应无二次确认自动显示已绑定。
4. 两位员工向各自 Bot 发首条普通消息，以便入站同步取得真实 `context_token`；机器人会回一句「已连接，之后会在这里推送。」（需 `P3_DELIVERY_ENABLED=true`）；检查 UI 「需要互动」恢复为正常。仅在受控小范围试投中打开发送开关，核对不同兴趣与消息路由、退订、解绑、同一日重复任务和推送窗口过期的用户侧表现。
5. 记录至少连续三天跨日真实送达和恢复、渠道数据授权及异常回执；达到验收门槛后再勾选 P3-04，按 GP 内容审核和供应商授权分阶段打开其它 P3 功能开关。旧版 Hermes Agent 对话审批不因通知扫码自动通过。

目前仅有代码和 Mock CI 作为合并时的验证证据；真正的扫码权限、持续送达与微信会话过期行为必须以部署后的员工试用为准。
